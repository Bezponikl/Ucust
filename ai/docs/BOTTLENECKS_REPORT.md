# Отчет по аудит узких мест, технического долга и отказоустойчивости «UCust.AI»

**Дата проведения аудита:** 29 июля 2026 г.  
**Версия подсистемы:** 2.1.0-SingleServer-LTX2.3  
**Назначение документа:** Комплексный технический аудит отказоустойчивости, узких мест производительности (bottlenecks) и логических рисков мультиагентного конвейера UCust.AI с формированием технического задания на оптимизацию.

---

## 1. Введение и общий контекст аудита

Мультиагентный конвейер UCust.AI управляется конечно-состоятельным автоматом (**FSM**) и объединяет 5 специализированных агентов. Ввиду использования локальных нейросетевых моделей (LLM Saiga 3), мультимодального видео-аудио движка (LTX-2.3 на базе ComfyUI) и внешней интеграции (Travity API, Telegram/VK парсеры), система имеет ряд критических точек отказа и потенциальных узких мест производительности при масштабировании.

Ниже представлен поагентный разбор уязвимостей и вектор их технической нейтрализации.

---

## 2. Поагентный анализ узких мест и рисков

---

### 2.1. `Agent_Interviewer` (Прием и первичная валидация анкеты)

#### 1. Критические точки отказа (Points of Failure)
* **Хрупкость неструктурированного ввода:** При передаче в анкету `UserQuestionnaire` неполных данных или строк с нестандартными спецсимволами (`NUL-bytes`, длинные фрагменты без пробелов, некорректный JSON в поле `competitors`) может возникать сбой валидации Pydantic или падение SQLAlchemy ORM при записи в `UserProfile`.
* **Блокировка базы данных:** При кратковременном разрыве соединения с PostgreSQL транзакция в `get_user_questionnaire` падала без авторетрая до внедрения SQLite-фолбэка. При конкурентном обновлении профиля возможен `Deadlock` в PostgreSQL.

#### 2. Узкие места производительности (Performance Bottlenecks)
* **Прямые блокирующие операции с БД:** Отсутствие L1-кэширования проверенных профилей в Redis приводит к повторным дисковым `SELECT`-запросам в PostgreSQL на каждом старте FSM.

#### 3. Семантические и логические риски
* **Отсутствие LLM-санитизации парсинга:** Агент не проверяет смысл введенных пользователем бизнес-целей и ниши. Если пользователь введет абракадабру или противоречивые цели ("Бизнес: Доставка пиццы. ЦА: Космические корабли"), агент не отбракует ввод, и искаженные данные уйдут аналитику и копирайтеру.

#### 4. Вектор оптимизации (Action Items)
* **Внедрение LLM-Gatekeeper:** Добавить легкий первично-валидирующий промпт (или правило), проверяющий осмысленность анкеты до сохранения в базу.
* **Redis Caching Layer:** Кэшировать валидированные `UserQuestionnaire` объекты в Redis по ключу `user_profile:{id}` с TTL 24 часа.

---

### 2.2. `Agent_Analyst` (Анализ рынка, веб-поиск и SWOT)

#### 1. Критические точки отказа (Points of Failure)
* **Падение внешних сетевых сервисов:** Зависимость от Travity/Tavily API (`api.tavily.com`), Telethon Telegram Client и VK API. Таймауты сети, блокировки IP или 429 Rate Limits способны сорвать переход в `MARKET_ANALYZED`.
* **Переполнение контекстного окна LLM:** При слишком объемной выдаче живого поиска Travity и парсинга Telegram длинный Markdown-текст в `"=== АКТУАЛЬНЫЕ ДАННЫЕ ИЗ СЕТИ ==="` может превысить контекстное окно `GenerativeCore` (LLM Saiga), обрезав SWOT-матрицу.

#### 2. Узкие места производительности (Performance Bottlenecks)
* **Отсутствие кэширования внешних вызовов:** Повторные поисковые запросы по одинаковым нишам совершают дублирующие платные HTTP-запросы к Travity API и нагрузки на VK/Telegram.
* **Синхронное ожидание ответа:** В текущей реализации `search_sync()` блокирует основной поток выполнения агента на время сетевого HTTP-запроса (до 10 секунд).

#### 3. Семантические и логические риски
* **Галлюцинации и шум из интернета:** Поисковая выдача может содержать рекламный спам или недостоверные статьи, которые агент без фильтрации заносит в SWOT-матрицу.

#### 4. Вектор оптимизации (Action Items)
* **Асинхронный HTTP Client & Circuit Breaker:** Использовать чистый `httpx.AsyncClient` с таймаутом 3.0с и паттерном Circuit Breaker (при 3 ошибках Travity мгновенно переключается на локальный кэш).
* **Поисковый кэш в Redis:** Кэшировать результаты веб-поиска по хэшу `SHA256(niche_query)` на 12 часов.
* **Сжатие текста (Text Summarization):** Прежде чем вклеивать результаты поиска в промпт, пропускать их через быстрый сжимающий сплиттер/суммаризатор.

### 2.3. `Agent_Copywriter` (Генерация поста и дедупликация)

#### 1. Критические точки отказа (Points of Failure)
* **OOM (Out Of Memory) на GPU:** Если инференс Saiga 3 выполняется на том же GPU, что и LTX-2.3 ComfyUI, одновременный запрос генерации поста и тяжелого видео приводит к `CUDA Out of Memory`.
* **Превышение порога дубликатов:** При малом объеме базы постов векторный фильтр `InMemoryVectorStore` может ошибочно браковать уникальные посты из-за близкого тематического словаря.

#### 2. Узкие места производительности (Performance Bottlenecks)
* **CPU-bound косинусное сходство в Python:** `InMemoryVectorStore` считывает векторный индекс в память и выполняет вычисления в GIL-потоке Python. При >100,000 постов скорость поиска упадет.
* **Медленный инференс LLM:** Генерация текста длиной 1500+ символов занимает от 3 до 8 секунд.

#### 3. Семантические и логические риски
* **Эффект "пластикового" языка:** Жесткие инструкции маркетинговых фреймворков (PAS, AIDA, PMHS) и запреты на служебные заголовки заставляют модель генерировать однотипные клишированные тексты ("Вам надоело...", "У нас есть решение...").
* **Снижение креативности из-за постоянной температуры:** Фиксированные параметры сэмплирования (`temperature=0.7`, `top_p=0.9`) не адаптируются под нишу.

#### 4. Вектор оптимизации (Action Items)
* **Миграция векторного поиска на pgvector / Qdrant:** Вынести поиск дубликатов из памяти Python в базы `pgvector` или `Qdrant`.
* **Динамическая температура сэмплирования:** Изменять `temperature` в зависимости от выбранного фреймворка (например, `PAS`: 0.6 для точности; `AIDA`: 0.85 для креативности).
* **Семантическая разбалансировка фреймворков:** Внедрить рандомизацию лексических конструкторов для избежания шаблонности.

---

### 2.4. `Agent_FactChecker` (Верификация и Reflection Loop)

#### 1. Критические точки отказа (Points of Failure)
* **Исчерпание попыток рефлексии (Circuit Breaker Failure):** При `correction_attempts >= 3` агент выбрасывает `RuntimeError("Не удалось устранить галлюцинации модели")`, полностью ломая задачу и переводя статус в `FAILED`.
* **Бесконечный цикл исправления:** Если `Agent_Copywriter` при повторных попытках генерирует новые недоказанные утверждаемые цифры, задача гарантированно уходит в фатальную ошибку.

#### 2. Узкие места производительности (Performance Bottlenecks)
* **Каскадный прогон инференса:** Каждая итерация рефлексивного цикла заставляет прогонять через LLM еще 2 полных запроса (FactChecker -> Copywriter -> FactChecker). Время отклика API вырастает с 4с до 25с+.

#### 3. Семантические и логические риски
* **Ложноположительные срабатывания (False Positives) на метафорах:** Фактчекер может принимать художественные метафоры ("наши продажи взлетели до небес") за невалидированные физические факты и удалять их.
* **Конфликт критериев фактчекинга и CTA:** Фактчекер может отбраковать CTA-призыв, если посчитает его не подкрепленным фактами из SWOT.

#### 4. Вектор оптимизации (Action Items)
* **Мягкий деградационный фолбэк (Soft Fallback instead of Crash):** Вместо выброса `RuntimeError` при 3 попытках — автоматически вырезать спорные предложения и принудительно проставлять `fact_checked = True` с пометкой в логах.
* **Двухуровневый фактчекинг:** Разделить проверку на "Жесткий фактчекинг цифр/имен" и "Мягкую оценку метафор".

---

### 2.5. `Agent_Visual_Director` (ComfyUI Headless & LTX-2.3)

#### 1. Критические точки отказа (Points of Failure)
* **Падение ComfyUI / Зависание воркфлоу:** Если ComfyUI сервис на `127.0.0.1:8188` недоступен, упал из-за CUDA ошибке или застрял в очереди, агент переходит на мок-фолбэк. Однако в продакшене без обработки ошибок это ведет к отсутствию готовых медиафайлов.
* **Несовместимость ComfyUI JSON-графа:** Любое изменение названий нод в ComfyUI ломает детерминированный граф `_build_comfyui_workflow`.

#### 2. Узкие места производительности (Performance Bottlenecks)
* **VRAM Bottleneck (Главное узкое место системы):** Генерация LTX-2.3 требует загрузки 6 тяжелых компонентов (`ltx-2.3-22b-dev`, `gemma_3_12B_it_fp4`, `spatial-upscaler-x2`, `video_vae`, `audio_vae`). При суммарном размещении на GPU с VRAM < 24 ГБ генерация даже одного видео вызывает длительный swap латентов на RAM диска, увеличивая время рендеринга с 15с до 180с+.
* **Синхронный `generate_media_sync`:** Использование `ThreadPoolExecutor` или `asyncio.run` блокирует ивент-луп FastAPI при локальном ожидании файлов.

#### 3. Семантические и логические риски
* **Рассинхронизация видео и аудио:** LTX-2.3 генерирует звук и видео параллельно, но при сложных текстовых промптах визуальный ряд и аудиодорожка могут не совпадать по динамике.

#### 4. Вектор оптимизации (Action Items)
* **Асинхронная очередь задач (Celery + RabbitMQ / Redis):** Категорически запрещено запускать рендеринг LTX-2.3 прямо внутри HTTP-запроса FastAPI. Вынести генерацию в асинхронную очередь задач с последовательным сервером очереди (GPU Task Worker limit = 1).
* **VRAM Governor / Model Offloading:** Настроить ComfyUI параметры `--highvram` / `--lowvram` для динамической выгрузки Gemma 3 из видеопамяти после кодирования промпта.

## 3. Сводная матрица рисков и решений

| Компонент / Агент | Главное узкое место | Риск отказа | Вектор решения / Техническое задание |
| :--- | :--- | :--- | :--- |
| **`Agent_Interviewer`** | Сырой невалидированный ввод | Падение ORM SQLAlchemy | Внедрить `Pydantic-sanitizer` + Redis-кэш профилей |
| **`Agent_Analyst`** | Синхронные вызовы Travity API | Блокировка потока, 429 Rate Limit | `httpx.AsyncClient` + Circuit Breaker + Redis кэш 12ч |
| **`Agent_Copywriter`** | "Пластиковый" язык фреймворков | Однотипный контент | Динамическая температура + `pgvector` дедупликация |
| **`Agent_FactChecker`** | 3 попытки Reflection Loop | Аварийный краш `RuntimeError` | Мягкая авто-очистка (Soft Fallback) вместо краша |
| **`Agent_Visual_Director`** | VRAM Out Of Memory в LTX-2.3 | Падение ComfyUI / GPU Swap | Очередь `Celery + RabbitMQ` (GPU Concurrency = 1) |

## 4. Дорожная карта оптимизации (Roadmap)

### Этап 1: Стабилизация и зашита от сбоев (Immediate Fixes)
1. Заменить `RuntimeError` в `Agent_FactChecker` на мягкую авторедакцию с флагом предупреждения.
2. Обернуть сетевой вызов `TravitySearchSkill` в асинхронный таймаут 3.0с с автоматическим переключением на fallback.

### Этап 2: Асинхронизация и Кэширование (Medium-term)
1. Внедрить **Redis** для кэширования профилей клиентов и результатов веб-поиска по нишам.
2. Перевести векторный поиск `InMemoryVectorStore` на расширение **`pgvector`** в PostgreSQL.

### Этап 3: GPU Очередь и Производительность (Production Readiness)
1. Развернуть **Celery + RabbitMQ** для изолированной очереди рендеринга видео в ComfyUI с жестким ограничением параллелизма (Concurrency = 1 на GPU).
2. Настроить мониторинг VRAM и автовыгрузку контекста текстового энкодера Gemma 3 в ComfyUI.
